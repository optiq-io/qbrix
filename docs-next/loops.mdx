## Who gets what

Every answer from `select` is one of two things:

- **A decision**, with a `request_id`. The loop chose an option, and an outcome for it teaches the loop.
- **The fallback**, with no `request_id`. The loop wasn't deciding for this request, and the `reason` says why.

Two separate things decide which one a request gets.

**Delivery decides who the loop serves.** A request is in the loop's delivery when it passes all three parts:

| Part | What it says | Left out |
|---|---|---|
| Schedule | Daily hours, from start until end (`09:00` to `18:00` decides from nine and stops at six; a start after the end runs past midnight), and a date it starts on, both in a named timezone | Always |
| Audience | Conditions on the request's context properties, all of which must hold | Everyone |
| Rollout | The share of the audience, 0 to 100 | 100 |

**The loop's state decides what they get.** Inside its delivery, a live loop gives the engine's choice, and a committed loop gives its committed option. A draft, paused or retired loop gives everyone the fallback, whatever its delivery says.

Delivery never picks an option. To give different people different options, tell the engine about them through context, and it learns who each option suits.

Everyone else gets the fallback, with the reason `outside_delivery`. Fallback answers are counted per loop by their reason, and never billed.

### An example

A loop is committed to `urgency`. Its audience is `device is mobile` and `country in NL, BE`, its rollout is 100, and its fallback is `control`.

- A phone in Amsterdam gets `urgency`, reason `committed`, with a `request_id`.
- A laptop in Amsterdam gets `control`, reason `outside_delivery`, with no `request_id`. Committing to an option never widens who the loop reaches.
- If the loop is paused, everyone gets `control`, reason `paused`.

### Conditions

A condition is a property, an operator and a value:

```json
{ "property": "country", "operator": "in", "value": ["NL", "BE"] }
```

| Operator | Holds when the property |
|---|---|
| `is`, `is_not` | equals, or doesn't equal, the value |
| `in`, `not_in` | is one of, or none of, a list of values |
| `contains`, `not_contains` | contains, or doesn't contain, the value, such as a word in a string |
| `gt`, `gte`, `lt`, `lte` | is greater than, at least, less than, or at most the value |

- **A request without the property never holds a condition about it**, whatever the operator. `country is_not NL` leaves out a request that sends no country. To include those requests, send the property.
- **A comparison the values can't make doesn't hold.** `orders gte 3` doesn't hold for the string `"4"`; send numbers as numbers.
- An audience takes up to 20 conditions, and `in` and `not_in` up to 100 values.

### Rollout

Rollout places each unit in one of 100 buckets, from its id and the loop's. A unit keeps its bucket on a loop, so it gets a steady answer, and raising the rollout only adds units: everyone in at 10 is still in at 50. Each loop places units independently, so the same people aren't always first in.

### Changing a delivery

`delivery_update` over MCP, or `PUT /api/v1/loops/{loop}/delivery`, changes any of the audience, rollout, schedule and fallback. A part you leave out keeps its value. A part you give replaces the whole part. It is one change, recorded with what it was before, and it can be undone. Every replica serves the new delivery within 30 seconds.

There is no end date. A temporary stop is a pause; when the choice leaves the product, retire the loop.

## What a loop learns from

A loop's **context** is the list of properties its engine learns from. Every property a request sends is recorded with its decision and can be used in the audience; the context says which of them the engine weighs when it chooses. Leibniz learns from context and needs one. Spinoza and Buridan don't use it.

```json
[
  { "name": "plan", "type": "categorical", "values": ["free", "pro"] },
  { "name": "seats", "type": "numeric", "min": 1, "max": 500 },
  { "name": "returning", "type": "boolean" }
]
```

| Type | Takes | Any other value |
|---|---|---|
| `categorical` | one of a few values worth telling apart | counts as `other` |
| `numeric` | a number, scaled between `min` and `max` and held at either end | |
| `boolean` | `true` or `false` | |

### Wire it first, then declare it

Change your app to send the properties with `select`, deploy it, then declare them. Until then nothing breaks:

- **A property you send but haven't declared** is recorded and usable in the audience; the engine ignores it.
- **A property you declare but don't send yet** is learned as its default, so it tells the engine nothing.
- **A value of the wrong type**, such as `3.5` for a categorical `plan`, is learned as the property's default too. `select` never fails over the context.

`GET /api/v1/loops/{loop}/context` shows which is happening. For the last day's decisions, it gives each declared property's count of decisions that carried it and of values that could be read, with the latest value. It also lists the properties sent but not declared. `context_update` answers with the same read.

### Changing the context

`context_update` over MCP, or `PUT /api/v1/loops/{loop}/context`, replaces the whole context; `null` clears it. It is one change, recorded with what it was before.

- **On a draft, or on Spinoza or Buridan,** it applies at once and can be undone.
- **On Leibniz, once launched,** it starts a new cycle, because what the loop learned no longer fits. Like any new cycle, it asks first by default and can't be undone. A committed loop is reopened first. Leibniz can't have its context cleared; start a cycle on another engine instead.

## Changing a loop

### Its brief

A loop's brief is what it is for and who owns it. Any member can change either, in any state, with `brief_update` over MCP or the `brief` part of an apply below. The owner must be a member of the workspace. It is one change, `brief.update`, and it can be undone.

On a draft, the brief also holds the options, the engine and the metric, and changing them changes nothing else. Once a loop is launched, they change with a new cycle instead.

### A new cycle

`cycle_start` over MCP, or `POST /api/v1/loops/{loop}/cycles`, starts a new cycle of a live or paused loop with new options, a new engine, a new metric, a new context, or any of them together. The new cycle pins the metric's newest version, and a metric of any type works: the engine is chosen again for it. The current cycle ends and stays readable. A new cycle can't be undone.

### Several edits at once

`POST /api/v1/loops/{loop}/edits` applies edits to a loop's brief, cycle, delivery and context together, in one go:

```json
{
  "brief": {"purpose": "lift checkout", "owner": "ana@example.com"},
  "cycle": {"options": [...], "engine": "leibniz", "metric": "purchase"},
  "delivery": {"rollout": 50, "fallback": "control"},
  "context": {"context": [{"name": "plan", "type": "categorical", "values": ["free", "pro"]}]},
  "reason": "what we learned this week"
}
```

- **One change per kind.** The brief, delivery and context are a change each, with the same request id, so history shows them as one apply.
- **At most one new cycle.** Once launched, the options, the engine and the metric start one `cycle.start`. It also takes the fallback, and the context when the new cycle's engine learns from it. A context change alone on Leibniz stays `context.update` and starts the cycle itself.
- **On a draft nothing starts a cycle.** The cycle part changes the draft's brief.
- **All or nothing.** If any part is refused, nothing applies, and the message starts with the part: `delivery: rollout: …`.

`POST /api/v1/loops/{loop}/edits/check` takes the same body and applies nothing. It answers with the changes the apply would make, the parts each carries, whether each can be undone, and the number of the cycle it would start.
