qbrix serves its own MCP server, at `/mcp` on the same address as the console. Add it to your client with one line, sign in once in the browser, and the client becomes a [connection](/docs/connections-and-autonomy) acting for you: it can read every loop and metric you can read, and make the changes your role allows.

Nothing extra runs: a self-hosted install serves `/mcp` from its first start.

## Connecting a client

Replace `https://qbrix.example.com` with your install's address.

| Client | How to add qbrix |
|---|---|
| Claude Code | `claude mcp add --transport http qbrix https://qbrix.example.com/mcp` |
| Cursor | In `~/.cursor/mcp.json`: `{"mcpServers": {"qbrix": {"url": "https://qbrix.example.com/mcp"}}}` |
| VS Code | `code --add-mcp '{"name": "qbrix", "type": "http", "url": "https://qbrix.example.com/mcp"}'` |
| Claude Desktop | Settings, Connectors, Add custom connector, with the URL `https://qbrix.example.com/mcp` |

Any other client that speaks MCP over HTTP with OAuth works the same way: give it the `/mcp` address.

The first time the client calls qbrix, it opens your browser to sign in and approve it. See [signing a client in](/docs/connections-and-autonomy#signing-a-client-in). An API key can't sign in to the MCP server: keys only ask for decisions and report outcomes.

## Tools

| Tool | What it does |
|---|---|
| `loops_list` | The workspace's loops, newest first: state, metric, whether a loop needs a look and why, share of decisions now, and the latest change with who made it, with the share of decisions that failed when qbrix paused the loop. Filter by state. |
| `loop_get` | One loop, led by what needs a look: each open [alert](/docs/alerts) with its value, such as how many decisions were made since the last outcome against how often one usually arrives, and then the alerts that recovered in the last 7 days. Then its purpose, options, metric, owner, [who it decides for](/docs/loops#who-gets-what) and what everyone else gets, [what it learns from](/docs/loops#what-a-loop-learns-from), state and current cycle, its latest change, this connection's level for each change to the loop (act on its own, act and notify, or ask first), the loop's most recent declined changes with their reasons, how to [mention the loop](/docs/github#mentioning-a-loop) in the pull requests it opens, and the `select` and `outcome` calls that wire it, in Python and JavaScript. A draft whose pull request [merged](/docs/github#ready-to-launch) names that pull request. A paused loop says who paused it, when and why: for a [safety pause](/docs/alerts), the share of calls that failed and over how long. |
| `loop_results` | A cycle's results: share of decisions per option, lift over an even split, decisions waiting to seal, and health, led by the loop's open alerts. |
| `loop_preview` | What `select` would return for a unit and its properties, recording nothing: the reason and the option, the part of the delivery that left the request out, or, while the engine decides, the loop's share over the last day. See [previewing a request](/docs/loops#previewing-a-request). |
| `metrics_list` | The workspace's metrics, with their type and window, and the loops that use each. |
| `changes_list` | Every change in the workspace, newest first: who made it and through which client, what it touched, each field before and after, why, and whether it can be undone. Waiting and declined changes are included, with who answered, where and why. Filter by who, kind, loop, metric and whether it can be undone. |
| `change_get` | One change by its id, with its status: applied, undone, waiting for approval, or declined, with who answered, where and why. |
| `loop_history` | A loop's changes and notes, newest first, declined changes included with their reasons, and the pull requests and commits that mention it. |
| `milestones_list` | What the workspace's loops reached, newest first: a draft's first call, a cycle's first window sealing, and a new option taking the lead. Filter by loop, metric, kind and time. |
| `workspace_summary` | The workspace since a date, 7 days back by default and 30 at most, in one call: for each live, paused and committed loop, each option's share of decisions then and now, lift over an even split, the [alerts](/docs/alerts) open at any time since then and how each ended, milestones, and its changes grouped by who made them and through which client; the drafts, naming those older than a week; and the workspace's change counts. Facts only: it ranks nothing and calls no option better. `GET /api/v1/summary` returns the same. |
| `docs_search` | This install's own docs, in the version it runs, so the code an agent writes matches its API. Give a `query` for the best sections in full, or a `page` by its slug to read one whole with its outline. An answer holds about 5K tokens at most, and each section comes with its link on qbrix.io. |
| `loop_create` | Creates a draft loop with its options and metric. |
| `loop_rename` | Renames a loop, in any state. Its key stays, so the code that calls it keeps working. |
| `loop_launch` | Takes a draft live: its first cycle starts. |
| `loop_commit` | Commits a live loop to one option: everyone it decides for gets it, and its outcomes keep teaching it. |
| `loop_reopen` | Reopens a committed loop: live again in the same cycle, with everything it learned. |
| `loop_retire` | Retires a live, committed or paused loop once its choice has left the product. Apps that still call it get its fallback. |
| `loop_pause` | Pauses a live or committed loop: everyone gets its fallback until it is resumed. |
| `loop_resume` | Resumes a paused loop to the state it was paused from. |
| `cycle_start` | Starts a new cycle of a live or paused loop with new options, a new engine, a new metric or a new context, all in one call. With a context, it asks first if either `cycle_start` or `context_update` does. |
| `cycle_reset` | Starts a new cycle with the same options, engine and fallback, learning afresh. |
| `delivery_update` | Changes [who a loop decides for](/docs/loops#who-gets-what): its audience, rollout and schedule, and the fallback everyone else gets. Any state but retired. |
| `context_update` | Declares [what a loop learns from](/docs/loops#what-a-loop-learns-from), and answers with which declared properties the last day's decisions carried. On Leibniz, once launched, it starts a new cycle and asks first like `cycle_start`. Any state but retired. |
| `engine_version` | Switches a launched loop's cycle between following its engine's major and staying on the minor it runs, keeping what it learned. See [its engine version](/docs/loops#its-engine-version). |
| `brief_update` | Changes [a loop's brief](/docs/loops#its-brief): what it is for and who owns it, in any state. |
| `metric_create` | Creates a metric with what it stands for, its type and its window. |
| `metric_update` | Changes a metric's window, its semantic (reworded, the same meaning or a new one) or, before any loop launched with it, its name. A new semantic starts a new cycle on every loop still deciding, asks first like `cycle_start` when it would, and can't be undone. See [Versions](/docs/metrics-and-outcomes#versions). |
| `metric_delete` | Deletes a metric no loop has used. |
| `note_add` | Adds a note to a loop's history. A note stays: a correction is a new note. |
| `change_undo` | Undoes an earlier change by writing its inverse as a new change, at your level for the change it undoes. |

- **A loop is named by its key or its id**, and a metric by its name or its id, in every tool.
- **Loop reads are concise by default.** They leave out each option's config and the share series; ask for `detail: "full"` to include them. `loops_list` returns 20 loops a page, up to 100, with a cursor to the next page.
- **Reads are marked read-only, and changes to an existing loop destructive**, so your client can ask you before it launches or pauses a loop.

Asking for decisions and reporting outcomes never happen over MCP. They belong to your app and its key, so a chat never teaches a loop something no user did.

## Changes

Every change tool takes a `reason`, a sentence on why. It is recorded in the loop's history beside who made the change and through which client, for example "Mustafa via Claude Code".

A change applies within your role and the connection's [autonomy](/docs/connections-and-autonomy#changes-that-ask-first), and its result says what happened:

- `status`: `applied`, `waiting` when the change asks first and hasn't been answered, or `declined`
- `change`: its id, its kind, whether it can be undone, and its link in the console
- the loop or metric as it is now: changed, or unchanged while the change waits

A change that asks first is put to you in your client, when the client can ask you through MCP: you approve it with one click, or decline it, with a reason if you like, without leaving the chat. The question goes to your screen, not to the model, so the agent can't answer it for you. The result then says `applied` or `declined`, and history records that you answered in that client, for example "approved by Mustafa in Claude Code". Your client's own decline button declines the change too, without a reason. If you close the question, or the client can't ask, the change keeps waiting with its link, and you answer it in your inbox in qbrix.

A waiting change applies nothing until you approve it. The agent checks on it with `change_get`, which says whether it is still waiting and, once answered, who answered, where and why. A loop's history lists its declined changes with their reasons, so an agent reads them before proposing the same change again. Only one change of each kind waits on a loop at a time; asking again names the one already waiting.

Creating a loop or a metric, renaming, committing, reopening, pausing, resuming and changing a delivery can be undone. Launching, retiring and starting or resetting a cycle can't.

**Repeating a call is harmless.** Clients and networks retry. The same change tool called again by the same connection with the same arguments within 5 minutes returns the first call's result and changes nothing twice. Change any argument, the reason included, and it is a new call.

## Prompts

Prompts are workflows you start yourself. Most clients show them as slash commands: in Claude Code, type `/mcp__qbrix__explain-loop checkout-headline`; elsewhere, pick them from the client's prompt or slash menu. A prompt reads nothing itself: it gives the agent the steps, and the agent calls the tools.

| Prompt | Argument | What it does |
|---|---|---|
| `start-loop` | `choice`, optional: the product choice, in a few words | Asks what is being decided and what result counts, proposes the options, picks or creates the metric, creates the draft, opens a pull request that wires `select` and `outcome` or `track`, then proposes the launch. |
| `explain-loop` | `loop`: its key or id | Explains what the loop is doing in plain words: share of decisions, lift over an even split, health and decisions waiting to seal, and what changed. Then proposes one next step that doesn't repeat a declined change whose reason still holds, or none. |
| `weekly-review` | `since`, optional: 7 days ago when left out | Reviews the workspace from `workspace_summary`: what needs a look first, what moved, where one option has held most of the decisions, and what changed and by whom. At most one proposal per loop. |

None of them makes a change until you agree.

## What qbrix tells your client

When a client connects, qbrix sends it these instructions, which most clients pass to their model. A client on the 2026-07-28 revision of MCP receives them from `server/discover`, an older one from `initialize`.

```text
qbrix runs loops. A loop makes one product choice live: for each request it picks one of its options, and the outcomes that follow teach it which serves people best.

Words: a loop has options; each request gets a decision; an outcome, or a tracked event, on the loop's metric teaches it. A cycle is one run of a loop's options and engine, and a new cycle learns afresh. Every write is a change.

Changes
- Every change tool takes a reason. Say why in a sentence; it is recorded in the loop's history.
- Launching a loop, starting a cycle and retiring a loop usually wait for a person's approval, and so does anything else that starts a cycle. Say so when you propose one, and check on a waiting change with `change_get`.
- Before proposing a change to a loop, read its declined changes in `loop_get` or `loop_history`. Respect any date or condition a reason names: offer to set a reminder in the person's own tools rather than proposing it again.

Reading
- `workspace_summary` says how the workspace's loops are going since a date; `loop_get`, `loop_results` and `loop_history` say one loop's.
- Speak in share of decisions and lift over an even split. qbrix ranks no option, and neither should you.
- When a shift in a loop follows a change, put the two side by side with both times and say "likely" at most, never "because".

Code
- `docs_search` answers how to write `select`, `outcome` and `track` for this install's version; `loop_get` gives one loop's exact calls.
- Put qbrix:<key> in the title or description of the pull requests you open for a loop, or qbrix/<key> in the branch name, so they appear in its history.
- When a pull request changes how the code sends a metric, record it with `metric_update`, naming the pull request in the reason: same if it still measures the same thing, new if it now measures something new, which starts a cycle on every loop using it.
- Context is wired first, then declared: send the properties with `select`, deploy, then call `context_update`; its answer says which arrived.
- Never call `select`, `outcome` or `track` from a chat: a decision made there teaches the loop something no user did. `loop_preview` shows what `select` would return, recording nothing.

The person can start `start-loop`, `explain-loop` and `weekly-review` for these workflows.
```

## When qbrix refuses

A refused call comes back as an error that says what to do next, for example:

- "Your role can't launch loops. Ask an admin of this workspace."
- "No loop with key or id checkout-hed. Did you mean checkout-headline?"
- "The loop checkout-headline is live already; launching applies only to drafts."

A viewer's connection can call every read tool, and gets the role error from every change tool. Each connection has its own request limit: 120 calls a minute, of which at most 30 changes. Past 120, a call is refused before any tool runs, with `429` and when to try again. Past 30, a change tool returns "This connection made 30 changes this minute. Try again in N seconds; nothing was applied." Reads keep working. A repeated change counts too, even when it returns its first result. Both numbers are settings of your install; see [connections on your own install](/docs/connections-and-autonomy#on-your-own-install).

## On your own install

Route `/mcp` and `/.well-known/oauth-protected-resource` to the API, beside the sign-in paths. The Docker Compose gateway and the Helm chart already do. See [connections on your own install](/docs/connections-and-autonomy#on-your-own-install).
