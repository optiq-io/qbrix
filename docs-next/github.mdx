GitHub is the one tool qbrix connects to itself, and it is optional. Once a workspace connects it, a pull request or commit that mentions a loop shows up in that loop's history.

## Connecting

An admin connects GitHub from the console, under Settings · GitHub. It takes one pass through GitHub's own pages, and nobody copies a key by hand:

1. Choose whether the app belongs to your personal account or to an organisation, and select **Connect**.
2. GitHub shows its "Create GitHub App" page, already filled in with this install's addresses. Keep the name or change it, and create the app.
3. GitHub asks where to install it. Choose the repositories qbrix may see.
4. GitHub sends you back to Settings · GitHub, which lists those repositories.

Each workspace creates its own app. An install that hosts several workspaces has one app per workspace, and events from an app only ever reach the workspace that created it. The app is private: it can only be installed on the account or organisation that owns it.

Connecting is a setting, not a change. It doesn't appear in any loop's history, and it can't be done over MCP or with a key. Only an admin connects and disconnects. Everyone in the workspace can see whether GitHub is connected, who set it up, and which repositories it can see.

To change which repositories qbrix sees, use **Change on GitHub** in Settings · GitHub, which opens the installation's page on GitHub.

## Mentioning a loop

A pull request or commit links to a loop only when it names the loop explicitly. Loop keys are ordinary words, so qbrix never links by guesswork:

| Where | How to mention `checkout-headline` |
|---|---|
| A pull request's title or description | `qbrix:checkout-headline`, or a link to the loop in the console |
| A pull request's branch | `qbrix/checkout-headline`, anywhere in the branch name: `ada/qbrix/checkout-headline` works too. A branch can't hold a colon. |
| A commit message | `qbrix:checkout-headline`, or a link to the loop in the console |

A bare `checkout-headline` links nothing, and neither does a link to another install. Both console links count: `/loops/checkout-headline` and `/next/loops/checkout-headline`, with anything after them.

One pull request can mention several loops, and each gets its own entry. A key a draft had before it was renamed still links to that loop, unless another loop has that key now.

Agents add the mention themselves: over MCP, `loop_get` tells an agent both forms for that loop, so the pull requests it opens link without anyone remembering to.

## What appears in history

| On GitHub | In the loop's history |
|---|---|
| A pull request that mentions the loop is opened | The pull request, its number, title, author and a link, as open |
| It is merged or closed | The same entry shows merged or closed, at the time it happened. Reopened, it shows open again. |
| A commit that mentions the loop reaches the default branch | The commit, its first line, its author and a link |

A squash merge's commit doesn't add a second entry when its pull request already has one. Commits on other branches don't appear until they reach the default branch. If a later edit removes the mention, the entry stays and still follows the pull request.

These entries aren't changes: they never alter the loop, and they don't appear on the Changes page. Read them in the loop's history, with the GitHub filter to see only them, or over MCP with `loop_history`.

## Ready to launch

When a pull request that mentions a **draft** is merged, the inbox of the person who created the draft shows "The code for Checkout headline is merged. Launch it?", with the pull request. A draft an agent created over MCP suggests to the agent's person. If several merged pull requests mention the draft, the suggestion shows the latest one.

The suggestion stays until the draft launches or is deleted; there is no dismiss. A pull request that is closed without merging never suggests, and neither does one merged after the loop launched.

qbrix never launches on its own, because a merge is not a deploy. Launching stays a change like any other: you launch the draft, or your agent proposes it. An agent sees the merged pull request in the draft's `loop_get`, and a launch it proposes asks you first unless you let it launch on its own.

## What the app can see

The app asks GitHub for these permissions, all read-only:

| Permission | Why |
|---|---|
| Pull requests: read | To see pull requests that mention a loop |
| Contents: read | GitHub only sends push events, which carry commit messages, to apps with this permission |
| Metadata: read | Required by GitHub for every app |

It subscribes to two events, `pull_request` and `push`. qbrix keeps only the title, number, author, state, time and link of what mentions a loop. It never fetches files or diffs, even though GitHub shows "Contents: read" as read access to code, and it can't write anything to GitHub.

The app's private key and webhook secret come from GitHub once, when the app is created. qbrix stores them encrypted under `PROXY_SECRET_BOX_KEY` (see [configuration](/docs/configuration)) and never shows them. If that key changes, qbrix can no longer act as the app: disconnect and connect again.

## GitHub must reach the install

GitHub tells qbrix about a pull request or commit by sending an event to this install's public address, `PROXY_PUBLIC_URL`. An install GitHub can't reach, such as one on a laptop or on a private network, can't link pull requests.

Settings · GitHub says so instead of failing quietly:

- **Before you connect**, when `PROXY_PUBLIC_URL` isn't a public `https` address: `localhost`, a private IP, or a name such as `qbrix.internal`.
- **A minute after you install the app**, when no event from GitHub has arrived. Check that the address is public and that nothing in front of qbrix, such as a proxy or a firewall, blocks `/api/v1/github/events/`.

As soon as an event arrives, the warning goes away.

### Trying it on a local install

A tunnel gives a local install a public `https` address. With [cloudflared](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/) installed, from the repository:

```bash
make dev-next-tunnel
```

It opens a quick tunnel to `localhost:8080`, needing no Cloudflare account, and starts the proxy with `PROXY_PUBLIC_URL` set to the tunnel's address. A quick tunnel's address changes every time it starts, so an app created through one stops receiving events when the tunnel closes. Disconnect it before you stop.

## Disconnecting

**Disconnect** in Settings · GitHub removes the app's installation on GitHub, then the credentials qbrix kept. Mentions already in loops' history stay.

The app itself stays on GitHub, owned by whoever created it. Settings · GitHub links to its page on GitHub, where its owner can delete it. Connecting again creates a new app.

If GitHub doesn't answer, nothing is removed, so you can try again. If the app was already uninstalled or deleted on GitHub, disconnecting only removes the credentials.
