A metric is what a loop improves: purchases, items added, revenue, a rating. It says which values count, how long a decision waits for its outcome, and what no outcome means, so qbrix can learn from every decision the same way without you getting those rules right by hand.

## What a metric is

A metric is a workspace object with four parts:

- **Name:** what your code sends with each outcome, such as `purchase` or `answer.rating`.
- **Semantic:** one sentence saying what the metric stands for, such as "The visitor completes a checkout." It is how people and agents tell two metrics apart.
- **Type:** conversion, count, value or score. It decides which values are valid and how outcomes add up.
- **Window:** how long a decision waits for its outcome.

Each [loop](/docs/loops) improves one metric, named when the loop is created. Several loops can share the same metric.

## Metric types

| Type | For | Valid values | Repeated outcomes | No outcome by the end of the window | Sealed |
|---|---|---|---|---|---|
| **Conversion** | Did it happen: a purchase, a sign-up, a click | 0 or 1 | The first one counts | 0 | At the first outcome, or when the window closes |
| **Count** | How many times: items added, messages sent | Whole numbers, 0 or more | Added up | 0 | When the window closes |
| **Value** | How much: revenue, minutes watched | Any number | Added up | 0 | When the window closes |
| **Score** | A rating on a known scale: satisfaction, a quality grade | Within the metric's range | The last one counts | Ignored: the decision teaches nothing | When the window closes |

A decision is **sealed** when its outcome is final. Nothing changes it after that, and only sealed decisions are learned from and counted in results.

- An outcome that isn't valid for its metric is refused with an error. qbrix never rounds a revenue figure into a conversion.
- A score metric declares its range when it is created, such as 1 to 5. No other type takes a range.
- The type also decides how a loop learns, so you never declare a reward type or rescale values yourself.
- An outcome sent twice with the same event id counts once, so retries are safe.

## The window

Every metric has a window, set when the metric is created. It defaults to 24 hours. The window starts at the moment of the decision.

- **When the window closes without an outcome,** qbrix seals the decision itself, with the type's value for no outcome. You never send zeros.
- **An outcome counts only if it happened and reached qbrix within the window.** Anything later is late: qbrix records it and never learns from it.

Choose the window from how long the outcome usually takes: minutes for a click, a day or two for a purchase. Too short, and real outcomes arrive late and teach nothing. Too long, and count, value and score decisions take longer to seal, so the loop learns more slowly. A conversion is sealed at its first outcome, so a long window costs it less.

<Callout type="tip">
A checkout loop improves `purchase`, a conversion with a 2 day window. On Monday at 10:00 a visitor sees option B. If they buy on Tuesday, the decision is sealed at that moment with 1. If they never buy, it is sealed on Wednesday at 10:00 with 0. If they buy on Thursday, the purchase is late and teaches nothing.
</Callout>

## Versions

A new metric starts at version `1.0`. Every decision records the metric version it was made under and is sealed by that version's rules, and every cycle of a loop records the version it started with.

A metric's window and semantic can change; its type and range can't. Every change is recorded on the metric and in the history of each loop using it, with the reason.

- **A new window** is a minor version (`1.0` to `1.1`). Loops follow it at once, without a new cycle: decisions made from then on wait for the new window, and decisions already open keep theirs.
- **A new semantic** is one of three:
  - **Reword:** the same meaning in other words. No new version.
  - **Same:** the same meaning, said anew, for example because the code now sends it from somewhere else. A minor version.
  - **New:** a different meaning. A major version (`1.1` to `2.0`) that starts a new cycle on every live, paused or committed loop using the metric, in the same change, so nothing learned under the old meaning mixes with the new. Each loop keeps its state: a committed loop stays committed to the same option. Drafts take the new version when they launch. This can't be undone.
- When code changes what it sends for a metric, record it here, with the pull request as the reason. A semantic may link the pull request too.
- **The name** is what code sends, so it can change only until a loop has launched with the metric.
- **Undo** a window, a reword or the same semantic on the metric's change: it comes back as a new change, a new minor version for anything that made one.
- **A metric can be deleted while no loop has used it.** Once a loop has, it stays.

To measure something of a different type, create a new metric and start a new cycle with it.

## Outcomes

An outcome is what happened after a decision: the purchase, the items added, the rating. Every answer from `select` carries a `request_id`. When you know the outcome, send it back with that `request_id`:

```bash
curl -X POST $QBRIX_BASE_URL/api/v1/outcome \
  -H "X-API-Key: $QBRIX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "request_id": "'"$REQUEST_ID"'",
    "value": 1,
    "id": "order-8841"
  }'
```

```json
{
  "id": "order-8841",
  "at": "2026-10-26T13:09:01.216000Z"
}
```

The value must be valid for the loop's metric (see [Metric types](#metric-types)). A `202 Accepted` means qbrix has recorded the outcome. It is learned from when its decision is sealed (see [The window](#the-window)), so a conversion teaches within seconds, and count, value and score outcomes teach when the window closes.

### Retries and timing

- **`id`** makes an outcome safe to send again: a repeat with the same `id` counts once. Use the id of what happened, such as the order id, so a retried request or a redelivered webhook never counts twice. Without one, qbrix assigns a fresh id, and every request is a separate outcome.
- **`at`** is when the outcome happened. Send it when outcomes wait in a queue or a batch job, so the window is judged by when they happened rather than when they arrived. It can't be earlier than the decision or more than 5 minutes ahead of now. Without it, the time of arrival is used.

### What qbrix records but never learns from

| Outcome | What happens |
|---|---|
| A repeat with an `id` already seen | Recorded as a duplicate |
| A conversion after the decision's first outcome | Recorded as a duplicate: the first one counts |
| Late: it happened, or reached qbrix, after the window closed | Recorded as late |
| Invalid for the metric | Refused with an error, and counted |
| A `request_id` that is altered, or from another workspace | Refused. An outcome is accepted only in the workspace that made the decision. |
| For a decision from an earlier cycle | Recorded in that cycle's history. A new cycle learns only from its own decisions. |
| A tracked event whose decisions are none for its metric | Recorded as unattributed, crediting nothing |
| A tracked event with only a unit, when the unit has no open decision in any loop that improves the metric | Recorded as unattributed, crediting nothing |
| An event matched by its unit to a decision that an exact outcome already credits | Recorded as a duplicate: an outcome that names its decision wins |

Many late outcomes mean the window is too short for how long the outcome really takes. Many unattributed events mean the decisions or unit ids sent with `track` don't match the ones sent with `select`.

### A metric's health

Every metric shows how its outcomes arrive and how they end, across every loop that improves it:

- **When outcomes arrive across the window:** for the last 7 days under the metric's current version, how long after its decision each outcome happened, the time by which half and 99% have happened, and the share that were late. This is what to read when setting the window.
- **A pulse:** outcomes a minute over the last 30 minutes.
- **Counts over the last 7 days:** learned, late, duplicate, unattributed and invalid.

A loop's results count its own outcomes the same way, for the last hour.

## Events from anywhere: track

The result often happens somewhere other than the decision: an order page, a payment webhook, a backend job. `track` sends an event for a metric, wherever it happens, and qbrix finds the decisions it belongs to.

- **`decisions`** is the decisions token: the `request_id`s a device was served, joined by `.` into one string. Code carries it to where the result happens (a cart attribute, order metadata, a payment's metadata), and the event credits exactly the decisions in it that were made for the event's metric. Each `request_id` is about 115 characters and signed, so the token can't credit a decision the device never received, and four decisions fit in a 500-character metadata value.
- **`unit`** is who the event happened to, the same `unit` sent with `select`. It is for events that never passed through a device holding decisions. In each loop that improves the metric, the event credits the unit's most recent decision that was open when it happened: the option the unit saw last before it.
- **`id`** and **`at`** work as they do for an outcome (see [Retries and timing](#retries-and-timing)).

```bash
curl -X POST $QBRIX_BASE_URL/api/v1/track \
  -H "X-API-Key: $QBRIX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "metric": "purchase",
    "value": 1,
    "decisions": "'"$REQUEST_ID_1.$REQUEST_ID_2"'",
    "id": "order-8841"
  }'
```

```json
{
  "id": "order-8841",
  "at": "2026-11-17T13:09:01.216000Z",
  "credited": 2
}
```

`credited` says how many decisions the event credits. It is `null` for an event sent with only a unit.

- An event that carries decisions is never also matched by its unit. When none of its decisions is for a loop that improves its metric, it is recorded and credits nothing.
- The same event credits every loop that improves the metric and has a decision in the token. Each loop seals its own decision.
- A decision made after the event's `at` is never credited.
- A `request_id` in the token that is altered, or from another workspace, is dropped and counted. The event is refused only when none of them verifies.

### Events with only a unit

```bash
curl -X POST $QBRIX_BASE_URL/api/v1/track \
  -H "X-API-Key: $QBRIX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"metric": "revenue", "value": 49, "unit": "customer-1", "id": "renewal-8841"}'
```

- qbrix matches the event to decisions a minute after it arrives, so a decision that reached qbrix just after the event is still found. Its outcome is judged as arriving then: an event in the last minute of a decision's window is late, and a metric whose window is under a minute can't be credited by unit. Send the decisions token when the window is that short.
- A decision that already has an outcome naming it, from `outcome` or from a token, counts a match by unit as a duplicate, whatever the metric's type. The same order sent both ways is never counted twice.
- When no loop that improves the metric has an open decision for the unit, the event is counted as unattributed on the metric's health.
- A loop fed only by events with a unit learns that outcomes arrive when they are matched. While qbrix is behind on its ledger, it waits before warning that outcomes stopped.

### From the browser

The JavaScript SDK remembers the decisions it served, one per loop, until each one's window closes. Every `track` from that browser carries the ones made for its metric, on any page and after a reload, with no plumbing:

```ts
const qbrix = new Qbrix({ apiKey: "optiq_..." });

await qbrix.select("checkout-headline", { unit: visitorId });
// later, on another page
qbrix.track("add_to_cart", 1);
```

To credit an order or a payment, carry the decisions to your server and send `track` from there:

```ts
// in the browser, at checkout
const decisions = qbrix.decisions("purchase");

// in the order webhook
await qbrix.track("purchase", 1, { decisions, id: order.id });
```

Ask for one metric's decisions where space is tight: four fit in a 500-character payment metadata value.

What the browser stores is decision ids and their loops, in `localStorage`, and no personal data. Whether your visitors' consent covers it is your app's call. Until it does, create the client with `storage: "memory"`, which keeps decisions only for the life of the page, and call `qbrix.setStorage("local")` once consent is given.

## Metrics API

The examples use these variables:

```bash
export QBRIX_BASE_URL="http://localhost:8000"
export QBRIX_TOKEN="your-sign-in-token"
```

`QBRIX_TOKEN` is a person's sign-in token: the `access_token` that `POST /api/auth/login` returns, which lasts 30 minutes. An API key only asks for decisions and sends outcomes and events: `select`, `outcome` and `track`. Every other route refuses a key with `403 FORBIDDEN`.

Every role can read metrics. Admins and members can create, change and delete them ([Roles and limits](/docs/roles-and-limits)). Each of those is recorded as a change in the workspace's history.

### Create a metric

<Endpoint method="POST" path="/api/v1/metrics" description="Create a metric at version 1.0" />

| Field | Type | Description |
|---|---|---|
| `name` | string | What code sends. Lowercase letters, digits, `_`, `-` and `.`, starting with a letter or digit, at most 64 characters. Unique in the workspace. |
| `semantic` | string | What the metric stands for, in one sentence. Required. |
| `type` | string | `conversion`, `count`, `value` or `score` |
| `range` | object | `{"lo": number, "hi": number}`, with `lo` below `hi`. Required for `score`, refused for every other type. |
| `window_seconds` | integer | How long a decision waits for its outcome, in seconds. Optional, default `86400` (24 hours). |

```bash
curl -X POST $QBRIX_BASE_URL/api/v1/metrics \
  -H "Authorization: Bearer $QBRIX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "purchase",
    "semantic": "The visitor completes a checkout.",
    "type": "conversion",
    "window_seconds": 172800
  }'
```

Response, `201 Created`:

```json
{
  "id": "070cc3402ef4412ebfda78d4852d2ee7",
  "name": "purchase",
  "type": "conversion",
  "range": null,
  "version": "1.0",
  "semantic": "The visitor completes a checkout.",
  "window_seconds": 172800,
  "created_by": "<user-id>",
  "created_at": "2026-10-26T12:54:14.848723+00:00",
  "updated_at": "2026-10-26T12:54:14.848724+00:00"
}
```

A score metric declares its range:

```bash
curl -X POST $QBRIX_BASE_URL/api/v1/metrics \
  -H "Authorization: Bearer $QBRIX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "answer.rating",
    "semantic": "The rating a user gives an answer, from 1 to 5.",
    "type": "score",
    "range": {"lo": 1, "hi": 5}
  }'
```

### Get a metric

<Endpoint method="GET" path="/api/v1/metrics/{metric}" description="Get a metric by its name or its id" />

```bash
curl $QBRIX_BASE_URL/api/v1/metrics/purchase \
  -H "Authorization: Bearer $QBRIX_TOKEN"
```

The response, `200 OK`, is the metric in the same shape as when it was created, with its `versions`, newest first. Each version has its `version`, `semantic`, `window_seconds`, `created_by` (`{"id", "name"}`), `created_at`, the `reason` given by the change that made it, and `changed`: what moved since the version before, as `{"field", "before", "after"}` for `window` and `semantic`.

It also has `health`:

- `arrival`: how the last 7 days' outcomes under the current version arrived. `buckets` counts them by how long after their decision they happened: 24 equal slices of the window, each `bucket_seconds` wide, then one bucket for everything after the window. `half_seconds` and `p99_seconds` are the times by which half and 99% happened, and `late_share` is the share that happened or reached qbrix after the window. An outcome that credits several decisions counts once for each.
- `counts`: the last 7 days' outcomes by how they ended, across every loop that improves the metric: `learned`, `late`, `duplicate`, `unattributed` and `invalid`.

### Change a metric

<Endpoint method="PATCH" path="/api/v1/metrics/{metric}" description="Change a metric's window, semantic or name" />

Admins and members can change metrics. Send any of:

| Field | Type | Description |
|---|---|---|
| `window_seconds` | integer | A new window, in seconds: a minor version. |
| `semantic` | string | What the metric stands for now. Sent with `semantic_change`. |
| `semantic_change` | string | `reword`, `same` or `new`, as in [Versions](#versions). |
| `name` | string | A new name, only until a loop has launched with the metric. |
| `reason` | string | Why, recorded in history. Optional. |

```bash
curl -X PATCH $QBRIX_BASE_URL/api/v1/metrics/purchase \
  -H "Authorization: Bearer $QBRIX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "semantic": "A paid order, sent from the payment webhook since https://github.com/acme/shop/pull/491",
    "semantic_change": "new",
    "reason": "https://github.com/acme/shop/pull/491"
  }'
```

Response, `200 OK`: the `metric` as it is now, the `change` (`{"id", "kind", "undoable"}`), and the `cycles` a new semantic started, one per loop:

```json
{
  "metric": {"name": "purchase", "version": "2.0", "...": "..."},
  "change": {"id": "8b1f0c5d0e4a4f6f9a1c2d3e4f5a6b7c", "kind": "metric.update", "undoable": false},
  "cycles": [{"loop": "checkout-headline", "cycle": 3}]
}
```

A change that changes nothing, or a semantic without `semantic_change`, is refused with `400 INVALID_METRIC`. A new name for a metric a loop has launched with is refused with `409 METRIC_IN_USE`, naming the loop.

### Delete a metric

<Endpoint method="DELETE" path="/api/v1/metrics/{metric}" description="Delete a metric no loop has used" />

```bash
curl -X DELETE $QBRIX_BASE_URL/api/v1/metrics/signup \
  -H "Authorization: Bearer $QBRIX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "never wired"}'
```

Response, `204 No Content`. A metric a loop uses, or ran in an earlier cycle, is refused with `409 METRIC_IN_USE`, naming the loop. Deleting can't be undone.

### Report an outcome

<Endpoint method="POST" path="/api/v1/outcome" description="Record the outcome of one decision" />

An API key can report outcomes, and so can admins and members.

| Field | Type | Description |
|---|---|---|
| `request_id` | string | The `request_id` that `select` answered with |
| `value` | number | The outcome, valid for the loop's metric: 0 or 1 for a conversion, a whole number of 0 or more for a count, any finite number for a value, within the range for a score |
| `id` | string | Optional. Makes the outcome idempotent; at most 256 characters. A fresh id when absent. |
| `at` | string | Optional. When it happened, ISO 8601; UTC when it has no offset. The time of arrival when absent. |

The response, `202 Accepted`, returns the outcome's `id` and `at`, as recorded. The example is under [Outcomes](#outcomes).

### Track an event

<Endpoint method="POST" path="/api/v1/track" description="Record an event for a metric, or a batch of up to 500" />

An API key can track events, and so can admins and members.

| Field | Type | Description |
|---|---|---|
| `metric` | string | The metric's name |
| `value` | number | Valid for the metric, as for an outcome |
| `decisions` | string | The decisions token: `request_id`s joined by `.`, at most 50. Either this or `unit` is required. |
| `unit` | string | Who the event happened to, at most 256 characters. Either this or `decisions` is required. |
| `id` | string | Optional. Makes the event idempotent; at most 256 characters. |
| `at` | string | Optional. When it happened, ISO 8601; UTC when it has no offset. |

The response, `202 Accepted`, returns the event's `id`, `at` and `credited`. The example is under [Events from anywhere](#events-from-anywhere-track).

To send several events in one call, send `{"events": [...]}` with 1 to 500 events. The response, `202 Accepted`, answers each event in order, with what was recorded or the error that refused it. One refused event never refuses the rest:

```json
{
  "results": [
    {"id": "order-8841", "at": "2026-11-17T13:09:01.216000Z", "credited": 1, "error": null},
    {"id": null, "at": null, "credited": null, "error": {"code": "INVALID_OUTCOME", "detail": "a conversion is 0 or 1, got 2"}}
  ]
}
```

### Errors

Errors carry a stable `code` and a `detail` that says what was wrong:

```json
{
  "code": "INVALID_METRIC",
  "detail": "a score metric needs its declared range"
}
```

| Status | Code | When |
|---|---|---|
| `400` | `INVALID_METRIC` | The name, type, range, window or semantic is refused. The detail names the rule. |
| `409` | `METRIC_NAME_TAKEN` | The workspace already has a metric with that name |
| `404` | `METRIC_NOT_FOUND` | No metric has that name or id |
| `400` | `INVALID_OUTCOME` | The outcome's value, `id` or `at` is refused. The detail names the rule, such as "a conversion is 0 or 1, got 2". |
| `400` | `INVALID_REQUEST_ID` | The `request_id` isn't one `select` gave in this workspace |
| `400` | `INVALID_DECISIONS` | No `request_id` in the decisions token is one `select` gave in this workspace, or it holds more than 50 |
| `404` | `LOOP_NOT_FOUND` | The loop of the outcome's decision can't be found |
